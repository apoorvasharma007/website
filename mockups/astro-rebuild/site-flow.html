Caching strategies

Caching is one of the highest-leverage performance interventions in distributed systems. A well-placed cache can reduce database load by 90% and cut latency by an order of magnitude.

Updated 29 Apr 2026Knowledge base
Appread Cachemiss Database

Cache-aside read path. A hit returns from the cache. A miss goes to the database and fills the cache.

Cache-aside

The application checks the cache first. On a miss, it fetches from the database and populates the cache.

python
def get_user(user_id: int) -> dict:
    key = f"user:{user_id}"
    cached = redis.get(key)
    if cached:
        return json.loads(cached)

    user = db.query("SELECT * FROM users WHERE id = %s", user_id)
    redis.setex(key, 3600, json.dumps(user))  # TTL: 1 hour
    return user
Pros

Only caches data that is actually read. A cache failure does not break the system.

Cons

Cold start latency, because the first request always hits the database. Stale data is possible after writes.

Note

Cache-aside is the right default for most read-heavy workloads. Implement it first and add complexity only when the access pattern demands it.

Write-through

Every write to the database also updates the cache synchronously, so the cache is always consistent with the database. The cost is that every write touches the cache regardless of read frequency, and unused data occupies cache memory.

Eviction policies

When the cache is full, the eviction policy decides what gets removed.

PolicyDescriptionUse case
LRUEvict the item not accessed longestGeneral purpose
LFUEvict the item accessed least oftenHot and cold data patterns
TTLExpire items after a fixed timeAll caches, as a safety net
FIFOEvict the oldest item regardless of accessSimple queues

LRU is the Redis default and a good choice for most workloads.

Cache sizing and TTL

Cache memory should hold the hot set, the data accessed by the top 80 to 90% of requests. Start with a cache large enough to hold 20 to 30% of your most-read dataset and observe hit rates. A hit rate below 80% suggests the cache is too small or the access pattern is too random to benefit from caching.

Building traininglogs: a Python pipeline for my gym data

TechFitness2 Apr 2026

How and why I built a parser that turns my messy training notes into structured JSON.

For years I kept training logs in a notes app. They were freeform text with inconsistent formatting, impossible to query. I wanted to fix this without switching to an app I did not control.

The solution was a parser that takes my existing format and outputs structured JSON. That is traininglogs.

The problem with training data

Most fitness apps are opinionated about how you should log. They give you dropdowns and fields. I do not train like that. I write notes while I rest between sets, and the format drifts based on how tired I am.

I needed a system that was tolerant of my input format but strict about its output.

The architecture

The pipeline has three stages.

  1. Intake. Parse freeform markdown into a rough intermediate representation.

  2. Model. Validate and type the data into Python dataclasses such as TrainingSession, Exercise and WorkingSet.

  3. Persistence. Serialise to a canonical JSON schema and write to storage.

Note

The dataclass layer is the most important piece. Every field has a type, and invalid data raises a TrainingLogValidationError instead of silently passing through.

The AI layer

I added an agent layer that lets me describe a session in natural language and have it structured automatically. This is the part I am still iterating on. The goal is prompts tight enough that the output is reliable without manual correction.

What I learned

Boring infrastructure matters more than the interesting parts. The parser is fine and the schema is fine. What makes the project useful is that the serialisation contract is strictly defined and versioned. Without that, any downstream tool breaks when the format drifts.

The deload week: what it is and why most people skip it

Fitness18 Feb 2026

A planned reduction in training load is not laziness. It is how you keep accumulating progress over months.

A deload is a planned week of reduced training, with lower volume, lower intensity, or both, inserted into a training programme to allow accumulated fatigue to dissipate before the next block.

Most people skip it. They feel fine, they are making progress, and a week of lighter training feels like wasted time. This is the wrong frame.

Fatigue masks fitness

During a hard block you accumulate both fitness and fatigue. Fatigue is quicker to accumulate and quicker to dissipate than fitness, so your performance during a hard block is lower than your real ceiling.

Note

A deload removes the fatigue faster than it removes the fitness. The week after, you often hit new personal bests because you can finally see your real strength.

What a deload looks like

TypeWhat changes
Volume deloadKeep intensity the same, cut total sets by 40 to 50%
Intensity deloadKeep volume similar, reduce weight to 60 to 70% of normal working loads
Full deloadBoth: lighter weight, fewer sets, shorter sessions

I prefer volume deloads. Keeping the weight meaningful stops the sessions feeling pointless, while the reduced volume lets systemic fatigue recover quickly.

How often

Every 4 to 8 weeks, depending on training age, life stress, and how hard the preceding block was. Newer lifters can often go longer between deloads. Advanced lifters may deload every 4 weeks.
